# Sentrame feasibility research — 2026-10-27

## Recommendation for review

The first release is the accepted complete WFS-only journey workflow; broader multi-app/version/invitation requirements remain the roadmap. The owner explicitly can emit standard OTel events and instrument accordingly. The remaining event work is to select names, meanings, safe linkage and exact coverage, not to reopen that ability. Continue comparing adaptation costs against a bounded journey-insight service. Standard telemetry, visit-only correlation, explicit healthy-loop/outcome semantics and a small Home Server footprint remain the differentiation; a graph alone is insufficient.

Selected architecture: static Svelte + TypeScript built with Vite, Go serving assets/API/SSE, SQLite with indexed evidence rows and bounded JSON attributes, and the maintained Collector OTLP receiver reused without a fork. Prefer a separate official Collector initially if in-process reuse creates more lifecycle/build complexity than it removes. Neither receiver packaging option is benchmarked here. See [design](../../openspec/changes/synthetic-journey-outcomes/design.md) for behavior and [decision register](../planning/sentrame-decisions.md) for unresolved gates.

### Narrow reasons not to build

1. **The observation contract still determines truth.** The owner can instrument events; select explicit commitment, completion-screen and end-reason observations plus safe visit/occurrence linkage. A backend cannot recover events not emitted or promote a browser screen observation into server persistence. Narrow any proposed observation that would require forbidden identity or unjustified collection; do not treat instrumentation ability as unknown.
2. **Low traffic may make rates uninformative.** Rare-path ranking among a handful of visits can suggest stories without supporting a decision. Start with counts and examples; stop if no reviewer can name an action the evidence would change.
3. **One-app bespoke analytics may be cheaper.** A bounded query over existing sanitized business events, reviewed periodically, may answer the question without a map, streaming service or configurable rule engine. Prefer that if live collaboration and reusable mapping are not needed.
4. **“Small” can hide distributed-systems work.** Durable acknowledgements, duplicates, source clocks, browser unload, late corrections, expiry and viewer revocation remain real even at low volume. Stop if their recurring maintenance exceeds the value of the product decisions.
5. **Existing infrastructure changes the economics.** A Home Server already running PostgreSQL and a Collector may favor reuse over a new SQLite service; an existing Rybbit/SigNoz instance may favor adaptation. Shared capacity and fault domains must still be counted.
6. **Privacy can conflict with desired detail.** Full stacks/messages and arbitrary resource attributes can contain secrets or personal content. If useful diagnostics require retaining disallowed data, narrow the question instead of silently weakening the boundary.

## Standard compatibility and producer behavior

The [OTLP specification](https://opentelemetry.io/docs/specs/otlp/) defines HTTP binary/JSON and gRPC Protobuf, standard signal endpoints, gzip support, signal-specific partial rejection counts and retry behavior. JSON has OTLP-specific ID/enum rules; use maintained parsers. Partial success is not retried. Transport acknowledgement does not establish exactly-once processing. These are interoperability obligations, not claims that Sentrame already supports them.

Proposed target matrix; every supported cell requires a real acceptance case before a compatibility claim:

| Signal | HTTP binary Protobuf | HTTP JSON Protobuf | gRPC Protobuf | Proposed use after receipt |
| --- | --- | --- | --- | --- |
| Logs/events | Target | Target | Target | Discover safe event shapes; configured business-step evidence and exceptions where context exists. |
| Traces/span events | Target | Target | Target | Linked execution/exception context; mapped actions when evidence is sufficient. Never assume one trace equals one visit. |
| Metrics | Target | Target | Target | Bounded sanitized receipt inspection; no path reconstruction or value-derived arithmetic before identity/temporality qualification. |
| Profiles | Excluded | Excluded | Excluded | Explicit unsupported response; no silent acceptance/discard. |

All target cells include uncompressed/gzip reception. HTTP uses `/v1/logs`, `/v1/traces`, `/v1/metrics`; gRPC uses the official service definitions. HTTP/1.1 and HTTP/2 handling, content types, errors, empty requests and decompression limits belong to receiver qualification. No gRPC JSON, arbitrary JSON webhook or “accept anything and return 200” transport is proposed.

The [exporter configuration guide](https://opentelemetry.io/docs/languages/sdk-configuration/otlp-exporter/) supports endpoint/protocol and per-signal configuration. A base endpoint can have signal paths added; per-signal endpoints must be configured correctly. Existing framework configuration takes precedence over a claim that all SDKs obey the same environment switch. The [JS exporter guide](https://opentelemetry.io/docs/languages/js/exporters/) limits browser export to HTTP/JSON or HTTP/Protobuf and identifies CSP/CORS/network exposure constraints; server gRPC availability does not make browser gRPC work.

The [SDK environment-variable specification](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/) lists batch-span scheduling at 5 seconds, batch-log scheduling at 1 second, and periodic metric export at 60 seconds as specification defaults. These are distinct mechanisms; implementations/configuration differ. Existing SDK processors/exporters should own batching and retries. Do not create a Sentrame universal batching layer or promise per-click immediacy. Browser process termination can still lose pending records; shorter flush intervals trade traffic/CPU for latency, not certainty.

The [Collector resiliency guide](https://opentelemetry.io/docs/collector/resiliency/) documents bounded memory queues, retry limits and optional file-backed queues. An intermediate queue can acknowledge before final storage. A persistent queue is not infinite or lossless: disk and retry exhaustion remain failure cases. Use existing mechanisms where needed, but show the real durable boundary. No message broker is justified before a quantified outage/volume requirement.

### Intake is not a business schema

Standard valid records without Sentrame fields must still ingest through configured app attribution. Unknown protocol fields are handled by the parser; arbitrary retained attributes are separately minimized. “Accepted with non-allowlisted fields omitted” differs from “protocol-invalid.” This deliberately differs from the earlier synthetic draft's reject-all-unknown-attributes profile.

Optional interpretation needs a random visit/session and meaningful named observations, obtained through existing instrumentation and configured field mappings. The OTel [`session.id` registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/session/) is still marked Development. It also defines `session.previous_id`, which Sentrame should not retain/use because cross-visit linkage is excluded. Do not present either key as universally emitted or required to receive telemetry.

The [log data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/) distinguishes occurrence/observed timestamps and optional trace context. Sentrame should add its own receipt timestamp rather than replacing occurrence time. Source sequence/context can strengthen order; a stable tie-break only stabilizes display, not causal truth. [Resource conventions](https://opentelemetry.io/docs/specs/semconv/resource/) provide service/runtime/deployment vocabulary, but automatic availability varies by SDK, detector and release build configuration. Unknown technical fields should not block intake.

### Independent challenge corrections

The [Astra review](../review/post-review-disposition.md) checked current official receiver code. The [logs consumer path](https://github.com/open-telemetry/opentelemetry-collector/blob/main/receiver/otlpreceiver/internal/logs/otlp.go) and corresponding metrics path return an empty success response or an error, not per-item partial counts from an ordinary consumer. The initial reuse proposal therefore uses whole-direct-request prevalidation and atomic commit/rejection. [Error conversion](https://github.com/open-telemetry/opentelemetry-collector/blob/main/receiver/otlpreceiver/internal/errors/errors.go) requires explicit standard validation/retry statuses; a generic permanent consumer error does not reliably mean HTTP 400. The [batch processor](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/batch_processor.go) acknowledges enqueue and regroups records, so neither final durability nor original-SDK-envelope atomicity follows from that acknowledgement. These are source checks, not compatibility tests.

Initial metric analysis is narrowed to bounded sanitized receipt inspection. The [metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/) requires identity/temporality/interval distinctions before arithmetic; dropping a private stream dimension cannot justify silently merging streams or summing cumulative points. Cross-signal diagnostic records likewise are not automatically distinct exception occurrences.

The user further reports that WFS moves the user to a completion screen. This is an observable visit outcome to capture through optional standard instrumentation, not proof that such telemetry exists today. WFS's pinned [Discovery capability](https://github.com/AlexandreBrisebois/whats-for-supper/blob/0dc61dfce9a7bf7d55eafff08f57c10e3f237f7c/openspec/specs/recipe-discovery/spec.md) includes another member causing convergence and an already-converged initial view. Record completion-screen observation in the current random visit separately from the shared state, its cause and emitted end reason. Do not join household/person/round identities. Initial-hydration/re-entry eligibility remains a policy choice.

### Established Home Server and event workflow

The latest user direction fixes Docker Compose with an associated Compose file/`.env`, behind an existing shared Cloudflare Tunnel supplying HTTPS. The [deployment contract](../proposals/home-server-deployment-contract.md) records configuration and qualification boundaries without creating actual setup files. Edge HTTPS, connector-to-origin transport and application authentication are distinct. Cloudflare's current [gRPC guidance](https://developers.cloudflare.com/network/grpc-connections/) excludes Tunnel public-hostname gRPC; keep that routed matrix separate from origin capability. Its [streaming guidance](https://developers.cloudflare.com/tunnel/troubleshooting/) requires `text/event-stream` to avoid whole-response buffering. Neither source qualifies this actual shared route; no account/network configuration or traffic was inspected.

For the app workflow, steps map to emitted events; the owner chooses a goal from discovered events and sees ordered paths from their known beginning to the event. [OTel event conventions](https://opentelemetry.io/docs/specs/semconv/general/events/) describe named events using the logs data model. [Severity fields](https://opentelemetry.io/docs/specs/otel/logs/data-model/) classify warnings/errors separately from event names; exceptions carry their standard attributes and can also be encountered in qualified span events. Event/Warning/Exception are useful UI classifications, not a new transport or fourth OTLP signal. Existing SDK API support varies; configured safe-field mappings can preserve meaning without a mandatory Sentrame SDK. Severity alone neither fails nor ends a journey.

Accepted time-at-stage analysis adds median plus slower cases, with node size for duration and edge thickness for traffic. Stage entry/exit or start/end evidence, tab/visibility/idle context and occurrence pairing require a declared policy. Next-event fallback is estimated; missing ends are censored, and cognitive effort is not measured. Exact slower percentile/support/scale policies remain choices. No timing or deployment benchmark was run.

## Accessibility and access references

Use [Canadian practical guidance](https://www.canada.ca/en/government/system/digital-government/government-canada-digital-standards/build-accessibility-start.html) and the [GC Design System](https://design-system.canada.ca/en/accessibility/) as practical references. The GC page's stated baseline is WCAG 2.1 AA; the proposed Sentrame target is [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). Review keyboard operation (2.1.1), no keyboard trap (2.1.2), visible/unobscured focus (2.4.7/2.4.11), color independence (1.4.1), text/non-text contrast (1.4.3/1.4.11), pause moving updates (2.2.2), target size (2.5.8) and status messages (4.1.3). A table equivalent and tested recovery flow matter more than adding an accessibility badge.

For proposed viewer sessions, [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) supports secure cookie handling, lifecycle controls and independent session validation. The [token lifecycle guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) is an analogy for short-lived, scoped bearer redemption, not a claim that password-reset and invitation semantics are identical. Prefer server-side revocable grants, secure HttpOnly same-origin cookies, rate-limited passphrase login, bounded invitation use and explicit diagnostic-copy permission. These are design recommendations; exact lifetimes/redemption defaults remain unchosen; one-live-session read-only scope with explicit baseline/diagnostic grants is selected for later invitations.

[Exception conventions](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/) provide type/message/stack vocabulary and warn that messages may contain sensitive information. No confidence badge or AI root-cause engine is needed. A developer can copy allowed evidence and known gaps; proximity must never be promoted into causality.
