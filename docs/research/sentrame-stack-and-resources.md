# Stack and Home Server resource decision — review proposal

## Selected stack and evidence confidence

The selected stack is **Svelte + TypeScript/Vite static assets, Go, SQLite, and maintained OTLP components**. Docker Compose with its associated Compose file and `.env`, behind the existing shared Cloudflare Tunnel HTTPS route, is the established deployment direction. Serve assets, same-origin APIs and SSE from the app; compare embedded receiver versus a maintained Collector sidecar. Count incremental shared-connector capacity. No Redis, Kafka, graph database, Node production frontend or separate scheduler is justified yet. The [deployment contract](../proposals/home-server-deployment-contract.md) is a proposal document, not actual setup implementation.

Confidence is high that static delivery eliminates a production frontend server; medium that SQLite is a suitable first store at the eventual workload; low for any exact RSS/CPU/storage prediction before a workload and Home Server are known. This is an accepted stack direction, not measured deployment qualification; the alternatives below preserve comparative rationale. None of the options below was built or benchmarked.

## Frontend alternatives

| Candidate | Benefit for this use | Cost/limitation and decision |
| --- | --- | --- |
| Svelte + TS + Vite, static | Small reactive component model for mapping controls, filter state, list/table and SSE updates. [Vite](https://vite.dev/guide/) outputs static production assets. No per-request frontend process is required. | Adds a frontend compiler/toolchain; actual bundle, install and build peaks remain unmeasured. Selected because it balances the interactive controls with a small deployable shape. Use plain Svelte/Vite first; do not add Kit unless routing/prerender needs justify it. |
| SvelteKit static adapter | [Official static adapter](https://svelte.dev/docs/kit/adapter-static) produces static files; useful if route structure benefits. | Server hooks/form actions are unavailable as a static auth backend; all protected data remains in Go. More framework surface than the initial view requires. Credible alternative, not a second server. |
| Preact/React + Vite static | Familiar TS ecosystem and broad testing/component options; same production process advantage as Svelte. | React familiarity might outweigh bundle differences. Do not assume framework-name benchmarks predict this graph-heavy app. Choose if actual team maintenance cost is lower. |
| Go HTML templates + small JS or htmx | [htmx](https://htmx.org/docs/) supports server-returned HTML for interaction; very little build tooling can be required. | Graph state, filter preservation, streaming patches and rule preview still need JavaScript. Best cheaper alternative if table/sequence view solves the task and graph interactivity can stay modest. |
| Next.js | Alex already knows it; static export is possible for suitable routes. | His reported build/test cost matters. SSR is unnecessary for a private data viewer; selecting a server deployment adds another runtime by default. Do not inherit WFS or Rybbit's stack solely for familiarity. No claim that every Next deployment is intrinsically heavy. |

The graph library and data volume can dominate browser cost regardless of frontend. Start with table/sequence evidence plus a bounded graph; avoid a layout animation on every arriving event.

### Graph ecosystem

- **Cytoscape.js**, preferred first comparison: maintained graph interactions, directed/multiple edges and layouts. Its [performance guide](https://github.com/cytoscape/cytoscape.js/blob/unstable/documentation/md/performance.md) identifies edge/label/animation/pixel-area costs. The inspected [license](https://github.com/cytoscape/cytoscape.js/blob/unstable/LICENSE) is MIT. It avoids inventing selection, zoom and graph state machinery; accessibility still needs an equivalent table and explicit controls.
- **Sigma + Graphology**: [Sigma README](https://github.com/jacomyal/sigma.js/blob/main/README.md) targets thousands of nodes/edges through WebGL; [license](https://github.com/jacomyal/sigma.js/blob/main/LICENSE.txt) is MIT. Better candidate if graph size is genuinely large. More rendering/GPU/context handling and business-graph interaction work may be unnecessary for a small semantic step set. Source capability is not a measured frame-rate guarantee.
- **D3/custom SVG**: attractive for a small, carefully designed weighted graph with accessible labels; higher responsibility for layout, loops, interaction and incremental updates. A linear flow layout must not erase healthy loops to obtain a prettier picture.
- **No graph database**: query workload is app/time/version-filtered evidence and sequences, not arbitrary multi-hop relationships over a large heterogeneous graph. A graph renderer does not imply graph storage.

Proposed initial display envelope for later review: 100 semantic nodes/500 displayed edges, explicit “other paths” and paged sequence drilldown; worker layout only if measured main-thread blocking warrants it. These are illustrative limits, not approved product caps. Do not drop rare paths silently. Record p95 filter-to-render, UI long tasks, browser heap and frame smoothness on the actual target desktop/tablet, including high-DPI and reduced-motion settings.

## Backend and receiver alternatives

| Candidate | Why consider it | Principal tradeoff |
| --- | --- | --- |
| Go + maintained Collector receiver components | One service can own transactions, API, static assets and SSE. [Go targets amd64/arm64](https://go.dev/doc/install/source#environment); the Collector ecosystem is Go. | Component lifecycle, telemetry plumbing and module upgrades still need ownership. Importing receiver components does not provide a ready-made app or a proven small binary. Selected backend; receiver packaging must preserve the declared durable acceptance boundary. |
| Go app + official Collector sidecar | Reuses supported OTLP endpoints/configuration with fewer embedding decisions. [OTLP receiver](https://github.com/open-telemetry/opentelemetry-collector/blob/main/receiver/otlpreceiver/README.md) covers stable logs/traces/metrics; select only required components. | Two processes; extra configuration and queue/ack boundary. An upstream success can mean Collector acceptance rather than app commit. This may still be the lower maintenance-cost option. |
| Go direct handlers + generated OTLP definitions | Potentially less receiver framework surface; durable application transaction is direct. | Owns protocol behavior, gzip/JSON parsing, partial errors, gRPC and compatibility maintenance. Consider only if measured receiver cost is material; do not replace OTLP semantics or ship a proprietary producer. |
| ASP.NET Core minimal APIs, possibly AOT | Strong WFS team familiarity and official .NET protocol/exporter ecosystem; one app process is possible. [Native AOT documentation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/native-aot) discusses smaller deployment/startup/memory for applicable apps. | AOT has feature/library compatibility and platform build constraints; publisher template benchmarks do not establish this app's footprint. OTLP receiver reuse is less direct than Go. Credible if team productivity beats Go savings. |
| Rust service | Potentially efficient steady-state runtime and explicit memory ownership. | Receiver ecosystem integration and compiler/build time may dominate a small project. No evidence that manual protocol work is worth it here. |
| Node/TS service | Shared language with frontend; broad API/SSE ecosystem. | V8/runtime baseline and protocol receiver glue still need measurement. It does not inherently require Next.js. Credible if smallest maintenance burden; no unsupported numerical memory claim. |

Embedding uses the official receiver unchanged with whole-direct-request prevalidation and atomic commit before success. Its ordinary consumer does not expose per-item partial-success counts; the [independent review](../review/post-review-disposition.md) verifies that source limitation and explicit error-status requirements. An upstream async batch processor/queue changes acknowledgement timing and can merge/split original SDK envelopes. A sidecar still needs a destination receiver in Sentrame. Show each boundary and qualify any persistent queue. A custom distribution uses the [official builder](https://opentelemetry.io/docs/collector/extend/ocb/), without a protocol fork. Packaging is future work.

## Storage alternatives

| Store | Fit | Footprint/operation and rejection condition |
| --- | --- | --- |
| SQLite + indexed rows + bounded JSON, preferred | Embedded transactional evidence and read models, with no database process. [Appropriate-use guidance](https://sqlite.org/whentouse.html) supports app-local/server-side storage. | One writer at a time; long read scans and cleanup/checkpoint behavior need bounds. Use local storage on the Home Server host. Reject if concurrent writers/queries cannot meet the measured budget or a network-mounted database is required. |
| PostgreSQL + JSONB | Strong concurrency/indexing and an existing team skill set. [JSONB documentation](https://www.postgresql.org/docs/current/datatype-json.html) supports structured JSON indexing. | A separate database service with shared memory, connection/process, WAL, vacuum and backup costs. If already running on the Home Server, incremental cost could be lower than a new operational path; isolate schema/permissions and count shared impact. First fallback when SQLite's write/query envelope fails. |
| Linux Foundation DocumentDB | The [Foundation announcement](https://www.linuxfoundation.org/press/linux-foundation-welcomes-documentdb-to-advance-open-developer-first-nosql-innovation) identifies the open PostgreSQL-based project. [Project source](https://github.com/documentdb/documentdb/blob/main/README.md) provides BSON extensions and MongoDB gateway. This is not Amazon's managed DocumentDB service. | MongoDB-compatible BSON/query ecosystem is useful when already needed, but Sentrame has no established MongoDB compatibility requirement. PostgreSQL plus gateway/extensions adds more service/dependency surface than embedded SQLite. Choose if existing operations, BSON capabilities or shared tools justify that cost; do not reject it on an invented memory requirement. |
| DuckDB | Strong embedded analytical option for bounded offline exports/columnar analysis. | [Concurrency documentation](https://duckdb.org/docs/2.0/connect/concurrency) distinguishes its analytical/concurrency model. It should not become the first operational ingest/auth store merely because the product analyzes events. Consider later for approved offline workloads if SQLite analytical reads become expensive. |
| ClickHouse | Columnar analytics, compression and high-volume aggregation; already used by Rybbit/SigNoz. | Additional service/merges/partition management and nontrivial query/retention behavior. No measured scale justifies it initially; reconsider only if retained event volume and scans demand it. |
| JSON files or counters alone | Fewer initial dependencies. | Do not supply the transaction, indexing, correction and sequence behavior needed here. Pairwise counters cannot distinguish complete variants or recovery paths. A directory of mutable session JSON blobs also causes rewriting/locking and expiry complexity. |

SQLite's [JSON documentation](https://sqlite.org/json1.html) supports text JSON and its own binary representation; that JSONB is not PostgreSQL's format. Use indexed scalar columns for app, visit, event/receipt time, stable source ID, step, version and expiry, with allowlisted bounded JSON for optional attributes. Avoid repeatedly parsing an entire raw OTLP envelope or rewriting one growing JSON array per visit. Preserve ordered event rows and sequence memberships; add rebuildable counters only after real query evidence.

Commit durability must name its failure model. A process-restart test does not establish Home Server power-loss durability. The SQLite WAL documentation also distinguishes synchronous behavior: NORMAL can lose recent commits after power failure; a power-loss acknowledgement promise needs an appropriate setting such as FULL plus storage/fsync assumptions. Do not reduce that promise to obtain a faster benchmark. Long-lived SSE connections must not hold long-lived DB read transactions.

The [WAL documentation](https://sqlite.org/wal.html) requires same-host use, explains checkpoint starvation and notes WAL can grow under long readers. Keep the database on a genuine local Home Server volume, not an SMB/NFS share mounted by another machine; verify filesystem locking/fsync semantics. Bound reader duration and checkpoint/cleanup work. Pin an engine containing the documented WAL-reset fix (3.51.3+ or a documented fixed backport), including the version bundled by the selected driver. Logical deletion does not by itself prove erasure from free pages, WAL, backups or SSD media; define the threat/backup policy before making an erasure claim.

DocumentDB's current [getting-started guide](https://documentdb.io/docs/getting-started/) now includes a required extended index component as well as core/API/gateway, while the source README describes three broad components. The guide labels its local container an evaluation/development path and discloses default usage telemetry. Its [1.0 release notes](https://documentdb.io/docs/getting-started/release-notes-1.0/) advertise Linux amd64/arm64 images and packages; [Linux package guidance](https://documentdb.io/blogs/posts/linux-packages/) identifies Ubuntu 24.04/EL9 and PostgreSQL 17/18. One local container can run several processes, including PostgreSQL and gateway; one container is not one process. No verified idle/load RAM minimum was found in the consulted pages. Recheck exact image/architecture/version and operational policy before selecting it.

The same [1.0 release notes](https://documentdb.io/docs/getting-started/release-notes-1.0/) list a particularly relevant correctness risk: a gateway retry after a committed write loses its reply can apply a non-idempotent update such as `$inc` twice, even with `retryWrites=false`. They also list grouped-view query crashes and container upgrades that do not update an existing volume's extensions. These are documented release-specific issues, not reproduced findings or claims about every version. A counter design must not assume database wire retries are idempotent. Before selecting DocumentDB, verify the chosen release's fixes and replay/upgrade behavior; prefer unique evidence identities and rebuildable contributions over unguarded increments.

GitHub Connector inspection also found [issue 767](https://github.com/documentdb/documentdb/issues/767) open on 2026-10-27, with an author-reported reproduction on the RC2 gateway and examples of doubled increments after a lost reply. This corroborates the release-note concern; it is not a Sentrame-run reproduction or proof that every later commit remains affected.

## Resource model to fill before build approval

Home Server model, CPU/ISA, core count, installed/free RAM capacity details, storage/filesystem, free disk, shared workloads and hard numerical limits are unknown; the owner reports enough RAM and CPU options, so capacity is not an immediate blocker. So are average/burst signal rates, sanitized record size, exception size, active visits, query concurrency and browser target. Do not invent them. No numeric runtime budget is chosen here.

| State | Principal costs to measure | Bounding proposal and acceptance evidence |
| --- | --- | --- |
| Idle, no viewer | App/receiver heaps, SQLite caches, timer wakeups, open connections; disk health logs. | Record stabilized RSS/PSS or cgroup working set (and page cache), idle CPU time/wakeups, baseline image+DB/log bytes. Avoid polling at high frequency. Compare owner budget. |
| Continuous ingest | Decode/decompress allocations, bounded in-flight requests, writer batches/fsync, JSON projection, source identity index and SSE fanout. | Sweep owner-supplied average/burst rates and payload tails. Record p95/p99 ack latency, committed records/s, CPU core-seconds, peak memory, disk bytes/s/IOPS, write amplification, queue saturation and loss. No “durable” success on failed commit. |
| Historical query | Rows visited, sequence grouping, joins, sort memory/temp spill, counters/revisions and long-reader WAL growth. | Run defined 1-day/7-day/30-day app+version queries and one full path drilldown while ingesting. Record latency, rows scanned, CPU, peak memory/temp disk and ingest degradation. Bound response size and query timeout. |
| Cleanup/recovery | Expiry deletes, derived correction, free-page/WAL behavior, checkpoint/vacuum and startup replay. | Use controlled clock and crash/restart scenarios in a later isolated qualification. Record worst pause, reclaimed/logical bytes, WAL bound, no resurrected data and exact loss boundary. Do not perform a daily full vacuum by habit. |
| Viewer/browser | Network graph JSON, parsing, graph layout, edge labels, high-DPI canvas, SSE burst handling and retained heap. | Measure target browser filter response, layout blocking, heap after prolonged live use and reduced-motion/table operation. Aggregate server-side; batch render updates and preserve drilldown completeness. |
| Build/focused tests | Frontend compiler, TS/typecheck, Go receiver dependency compile, SQLite driver toolchain and test fixtures. | Record cold/warm wall time, peak RSS, cache/download bytes and test selection on the developer/CI machine. Build off-Home Server by default. No assumption that a static frontend makes its build free. |
| Broad browser/seam tests | Browser install/launch, real temporary DB and protocol endpoints. | Run only affected integration cases during red/green; bounded final checks for the selected behavior. Do not run all broad browser suites after prose edits. |

Planning relation: peak ingestion memory includes baseline + concurrency × decoded request size + queue contents + DB caches + transient projection copies. Compressed request bytes do not bound decoded bytes. Query memory adds grouping/sort/result buffers; browser graph cost depends on visible elements and layout, not retained server rows alone. CPU and disk cannot be inferred from event rate without payload, fsync, index and query details.

Time-at-stage adds bounded occurrence pairing, visibility/idle evidence where emitted, duration quality and percentile-query work. Measure those records/indexes and live refresh costs too; no per-millisecond render or unbounded sort is assumed. Median plus slower cases and size/traffic encoding are accepted, while exact slower percentile, sample threshold, activity/fallback policy and node scale remain design choices. Stage-duration computations come from qualified event/span evidence; this does not silently enable general metric arithmetic.

### Thirty-day growth scenarios — arithmetic, not benchmarks

Assume **2 KiB per accepted record including a provisional index/share allowance**, no compression claim, steady rate and 30 days = 2,592,000 seconds. This is an illustrative input, not measured WFS data. Exceptions can be much larger. Signal volume includes accepted technical records, not just product steps.

| Accepted records/second | Records in 30 days | Provisional retained bytes (GiB) | With illustrative 50% working headroom (GiB) |
| ---: | ---: | ---: | ---: |
| 0.1 | 259,200 | 0.49 | 0.74 |
| 1 | 2,592,000 | 4.94 | 7.42 |
| 10 | 25,920,000 | 49.44 | 74.16 |
| 100 | 259,200,000 | 494.38 | 741.58 |

Formula: `rate × 86,400 × 30 × stored_bytes_per_record / 2^30`. Headroom is illustrative, not a guarantee: add measured WAL, temp sorts, backups, indexes above the assumption, aggregate tables, queue disk, images and logs. If average stored bytes double, retained growth doubles. Cardinality and write amplification change cost independently. Retention bounds duration, not incoming volume; an all-technical-signals default can overwhelm a small disk even when product event traffic is tiny.

“Record” is an illustrative accounted storage unit in that table, not a universal OTLP request or signal object. Real accounting must separately measure log records, spans, expanded span events, metric points, histogram buckets/attributes, sequence memberships and their bytes. Initial metrics support is receipt inspection; no value-derived summary is promised before stream identity/temporality survives privacy projection. This prevents the same table from hiding signal expansion or invalid metric arithmetic.

The accepted 12-month summary history requires bounded count/conversion and mergeable timing structures, with grains/dimensions/precision selected before implementation. Never average bucket medians. Keep source correction membership only within its documented horizon, not as hidden long-lived visit tracking. Counter-only summaries cannot reconstruct full paths/loops/individual outliers after 30-day detail expiry; disable that drilldown and expose unsupported queries. Summary storage growth must be measured in addition to the 30-day detail arithmetic.

## What would change the recommendation

- Existing managed PostgreSQL/Collector capacity and team familiarity could favor their reuse.
- High sustained ingest with 30-day multi-signal detail and concurrent analytics could move storage to PostgreSQL or ClickHouse, or require narrowing retained signals under explicit policy.
- A very small semantic step set and table-first task could favor Go templates plus minimal JS.
- The receiver's measured module/build/runtime cost could favor a sidecar over embedding; compatibility must remain intact.
- Exact Home Server CPU ISA and image/runtime tests can exclude an otherwise credible candidate. Go target support, Node/.NET release support and database driver availability must all match the actual OS/libc/architecture. CGO SQLite needs target C toolchains; a pure-Go driver removes that requirement but must still be assessed for correctness, footprint and bundled engine version.
- No new fact justifies a benchmark app now. The next step is review of this proposal and owner-supplied constraints, not implementation.
