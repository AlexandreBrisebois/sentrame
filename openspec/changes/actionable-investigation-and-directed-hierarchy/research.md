## What actually happened to ID filtering

The current source still has an exact correlation-scope field: `web/src/Workspace.svelte:495`, in **Time & filters → Advanced: exact times or correlation ID → Correlation ID (optional)**, with the placeholder “Paste a known session or operation ID”. `query()` sends it as `scope` (`:197`); server journey and evidence filtering use equality (`internal/app/query.go:531,554`). Thus “removed field” is not established by repository history. It is a discoverability/workflow failure in the inspected implementation. The field was already nested under Advanced in commit `5738712` (`web/src/App.svelte:227`) and remained there after extraction into the multi-app workspace in `2923b59` (`web/src/Workspace.svelte:257`). There is no evidence here of a recently visible session search being deleted. An unrecorded deployed build, other branch or older UI remains possible and must not be asserted as fact.

Three IDs are currently easy to conflate: anonymous session/operation scope, derived journey ID, and trace ID. Scope may contain multiple journeys and browser tabs; it is not a person. A journey ID identifies one derived journey under its context. Trace ID identifies distributed structural telemetry and cannot substitute for session correlation. `internal/app/intake.go:68` reads `session.id` into `Scope`; `JourneyStory.svelte:25` displays `journey.id`; `Traces.svelte:25` selects traces.

The newer **Matching journeys** “Path search” cannot find either journey or session IDs: `web/src/investigation.ts:65–69` filters only the joined `j.path` text, status and start time. Displaying a journey ID in a disclosure (`MatchingExamples.svelte:47`) does not make it searchable. The source retains a **Follow this visit/operation** action in the separate Ordered journeys tool (`Workspace.svelte:505`), but `JourneyStory.svelte:23–42`, used by Matching journeys and Journey timeline, lacks that action. Alex's report is consistent with this split even though the field survives.

## Directed hierarchy recommendation and alternatives

Recommend a **directed prefix hierarchy for path exploration**, with an exact-session selection showing the ordered occurrences of its journeys. A node's display identity is the full uninterrupted observed prefix (plus view/cohort context); its stage label remains a separate semantic identity. Consecutive A→A can be grouped only as an explicit expandable presentation with the original occurrence count and evidence references. A→B→A must show distinct A occurrences, not a cycle that erases ordinal position. Existing `prefixTree()` (`investigation.ts:39–52`) is useful groundwork, already bounded at 32 steps/200 visible nodes/5 initial branches and stops at source gaps. It should be reused or reconciled rather than introducing a contradictory second path-count model.

The price of honest prefix identity is that visually identical later stages do not merge across different prefixes. A→B→D and A→C→D show separate D nodes. Label these as the same stage at different path occurrences; offer inspect all occurrences of stage D and a compact alternate transition overview. Do not draw a fabricated rejoin in the hierarchy. If an explicit rejoin view is later chosen, it must retain incoming prefix provenance and prevent unsupported path combinations. This was an alternative considered during research; design.md recommends the prefix hierarchy and preserves aggregate views separately. Review may revise the recommendation before implementation.

| Model | Strength | Cost / false inference to avoid | Suitability |
|---|---|---|---|
| Directed layered aggregate graph | Compact shared stages, branches and rejoins; supports feedback edges. | Stage identity collapses repeated ordinal occurrences; SCC ranks cannot describe every session's progression. Layout cycle-breaking must never reverse underlying evidence direction. | Keep as a clearly labeled transition overview, or choose only if prefix expansion/drilldown is mandatory. |
| DAG of stage × ordinal | Repeats can advance by ordinal; later same-stage occurrences are distinct. | Merging at the same ordinal can invent cross-prefix combinations; ordinal is not elapsed time or causal depth. | Useful bounded alternative with explicit provenance; weaker exact-path fidelity than prefix hierarchy. |
| Sankey | Encodes traffic volume effectively with explicit denominators. | Conventional d3-sankey requires acyclic input; loops need unfolding or a different renderer. Width is not probability, unique people, duration or proof of conservation under clipping. | Secondary aggregate comparison; not the primary exact-session investigation model. |
| Directed prefix trie | Exact ordered prefixes, safe branch counts and repeated occurrences; aligns with existing Sequence flow and anonymous ID lookup. | Duplicates shared suffixes, grows quickly, cannot merge true-looking rejoins without losing prefix identity. | Recommended primary hierarchy; bounded expansion plus exact evidence and stage-wide cross-reference. |

Start means first retained/captured eligible occurrence under the selected policy; end means captured boundary or labeled observation limit. Goal markers mean only explicitly configured goal evidence. Horizontal layers represent ordinal progression, never wall-clock intervals. Distinct definition/app-version cohorts must stay visible or be separated; compare matching semantics explicitly. Outliers cannot disappear into “Other”: disclose omitted support and provide bounded exact-ID or branch expansion. Parallel server requests introduced by the sibling change require concurrency/uncertainty markers and must not be falsely converted to causal sequence by this layout.

## Primary-source comparison, accessed 2026-10-31

These sources informed interaction patterns, not a feature checklist or a claim that their collection/privacy models fit Sentrame.

- [PostHog User paths](https://posthog.com/docs/product-analytics/paths): links path selection to focused start/end exploration and supporting sessions; its docs explicitly distinguish path transition frequency from funnel populations and disclose path limits. Adopt the observation→supporting evidence pattern and explicit denominator. Do not import person identity, replay collection, raw URL path breakdowns, cohort marketing workflows or drop-off interpretation.
- [Amplitude Journeys visualizations](https://www.amplitude.com/docs/analytics/charts/journeys/journeys-understand-visualizations): settings carry between views; branches can be expanded and events can anchor exploration. Docs distinguish session boundaries from true events and describe differences from funnels. Adopt persistent investigation context and explicit path rules. Do not import their person-based conversion assumptions or treat a synthetic session end as a successful goal.
- [Eclipse ELK Layered](https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html): primary algorithm documentation describes layers emphasizing edge direction, crossing minimization, self-loops, multiedges and cycle-breaking options. This shows a layered graph can contain loops; it does not make data a tree or prove causality. An eventual library choice needs bundle/performance and deterministic-layout evaluation; no dependency selection is made by this spec.
- [D3 hierarchy stratify](https://d3js.org/d3-hierarchy/stratify): requires one root and no circular relationships. This supports distinguishing true tree data from general transition graphs. A prefix trie is a deliberate projection with duplicated stage labels, not merely feeding aggregate stage edges to a tree API.
- [D3 Sankey source and README](https://github.com/d3/d3-sankey): documents directed acyclic networks. This is direct evidence against assuming ordinary Sankey layout accepts arbitrary session loops. Sentrame's current custom renderer already handles return lanes (`graph.ts:99–120`); replacing it is not implied.
